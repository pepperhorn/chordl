# frames → chordl-guitar Migration

**Date:** 2026-08-09
**Status:** approved — design agreed; phase B has an implementation plan (`../plans/2026-08-09-chordl-guitar-gap-closing.md`), phase A's plan lives in the `frames` repo. **Nothing has been implemented.**

**Progress note, 2026-09-07:** re-audited both repos. Phases A–E are all unstarted. Two facts below have changed since 2026-08-09 and are corrected in place: `chordl-guitar` is now actually published to npm (0.2.0, in the 2026-09-01 six-package release), and `frames` has since taken a dependency on it — see "What has already happened in frames" below.
**Context:** sub-project 2 of `docs/superpowers/specs/2026-08-08-chordl-guitar-boundary-design.md`, which named this work but deliberately left it undesigned until the package landed.

## Problem

`frames` vendors its own chord-shape lookup, instrument config, and pitch math. `@pepperhorn/chordl-guitar` now owns all three, verified against all 4,183 chords-db positions. The boundary spec assigns frames the interface layer only: Astro pages, the rendering pipeline, the API surface, and the Workbench UI.

Retiring frames' vendored modules is not a mechanical find-and-replace. Four capabilities frames depends on have no equivalent in the package, two representation mismatches fail silently rather than loudly, and the module carrying the public HTTP contract has no tests at all.

## Decision

Five phases. `frames` consumes `@pepperhorn/chordl-guitar` from the **npm registry**, not through a `file:` link or a workspace. Characterization tests come first, before any dependency change.

## The constraints that shaped this

### frames cannot use `workspace:` or `file:`

`frames` is a separate git repository using **npm**, with its own `package-lock.json` and no `packageManager` field. It is not a member of any workspace and is not a subdirectory of the chordl repo.

- **`workspace:`** requires a shared pnpm/yarn workspace. Two separate repos cannot have one without a repo merge.
- **`file:../chordl/packages/chordl-guitar`** works locally but breaks deployment. `frames/Dockerfile` runs `npm ci` after `COPY package*.json ./` and *before* `COPY . .`, so a path outside the build context cannot resolve — the image fails to build. A `file:` link also does not run the dependency's build, and the package's `dist/` is gitignored, generated by `pnpm build:data && tsc`.

**Publishing to the registry is the only option that leaves the Dockerfile untouched.** The package already declares `publishConfig.access: "public"`.

**Enabling fact:** `chordl-guitar` depends only on `@tombatossals/chords-db` and `svguitar` — **no workspace dependencies**. It publishes standalone; `chordl-core` and `chordl-voicings` need no coordinated release.

### Four capability gaps

| Gap | Where it bites | Resolution |
|---|---|---|
| `CHORDS_DB` raw enumeration | `ChordWorkbench.buildPresets` walks the whole library; `apiFrame` looks up by `(key, suffix)`, not by label | **Add to the package** (phase B) |
| `patch` (MusyngKite soundfont name) | `tab/playback.ts` — audio breaks without it | **Stays in frames** — playback is frames' concern |
| `presetSource` | `ChordWorkbench.tsx` help text | **Stays in frames** — UI copy |
| `BASS_PRESETS` | ~110 lines of hand-fingered bass shapes | **Generated** by extending power chords to bass (phase B) |

`patch` and `presetSource` stay because the boundary spec's non-goals for the package exclude rendering, layout, and product presentation. Bass power chords are chord-shape data, which the spec assigns to the package — and bass strings are all perfect fourths (`bass4` openMidi `[28,33,38,43]`, differences 5,5,5), so the existing root/+2-frets rule transfers unchanged.

### Two representation mismatches that fail silently

**String order.** `frames`' `tab/instruments.ts` stores `openMidi` **high→low** (string 1 first); the package stores it **low→high** (chords-db index order). `tab/pitch.ts` reads `openMidi[note.string - 1]`, which depends on the high→low order. Swapping the table without reversing produces wrong pitches for every note, with no type error — only `pitch.test.ts` catches it.

Ukulele makes this unrecoverable by inspection: its reentrant high-G tuning means `[67,60,64,69]` is not sorted, so the order cannot be restored by sorting.

**Instrument ids.** frames has three disjoint id universes: `InstrumentId` (`guitar | bass | ukulele | guitar-top3`) for chord and scale mode and the public API, `TabInstrument` (`guitar | bass4 | bass5 | ukulele`) for tab mode, and `InstrumentUi` (`guitar | bass | ukulele`) inside `TabWorkbench`. The package has one: `guitar | ukulele | guitar-top3 | bass4 | bass5`.

**`"bass"` is a public API value** — documented in the `GET /api/frame` usage string. It must keep working, aliased to `bass4` at the boundary.

### The contract is untested

`apiFrame.ts` has **no tests**. Neither do `instruments.ts` (including `dbPositionToChord`, the highest-risk string-order function in the repo), `notes.ts`, or `tab/chordLookup.ts`. Between them these own: the four instrument branches, `positionIndex` semantics, the exact 400 message strings, and the `notes` / `noteNames` / `X-Note-Midi` response fields.

Migrating untested contract code offers no way to distinguish a successful migration from a broken one.

### `positionIndex` is a raw index

`/api/frame` accepts `positionIndex` and uses it as a direct index into `entry.positions` in chords-db's stored order. Anything that reorders, filters, dedupes, or canonicalises positions — which is what `selectVoicings`, `canonicalPositionIndex`, and `duplicateVoicingMap` exist to do — changes what `positionIndex: N` renders.

`lookupGuitarChord` preserves `entry.positions` verbatim, so index stability is achievable, **but only if frames indexes the raw `positions` array and never a selected or canonical subset.**

## Phases

| | Phase | Repo | Depends on |
|---|---|---|---|
| **A** | Characterization tests | frames | — |
| **B** | Package gap-closing, published as 0.3.0 | chordl | — |
| **C** | Chord and scale migration | frames | A, B |
| **D** | Tab migration | frames | C |
| **E** | `scales.ts` split | both | C |

A and B are independent and can run in parallel — different repositories.

### Phase A — Characterization tests

**No production code changes. No dependency changes.**

These assert **what the code does today, not what it should do.** If a test reveals a bug, it is recorded and left alone: the migration's job is to preserve the contract, and "fixing" it here would move the target that phases C and D are measured against.

- **`src/lib/apiFrame.test.ts`** — all four instrument branches; `positionIndex` at 0, valid, and out of range, with the exact 400 strings (`Position N out of range (have M)` leaks the count, making it observable); raw-`fingers` passthrough ignoring `key`/`suffix`; `guitar-top3` padding strings 4–6 as `"x"`; the settings merge order (`baseSettings` → scale `fretSpan` override → caller's `settings`); scale-path validation errors for invalid key and scale.
- **`src/lib/notes.test.ts`** — `stringFretToMidi`, `notesFromChord`, `notesFromScaleDots`, `midiToName`. These feed the public `notes`, `noteNames`, and `X-Note-Midi` fields, so their output is contract.
- **`src/lib/instruments.test.ts`** — `dbPositionToChord`: the string-order flip, barre span and finger inference, muted and open handling.
- **`src/lib/tab/chordLookup.test.ts`** — `lookupChordFrets`: absolute-fret derivation from `baseFret`, position-0-only behaviour, enharmonic and suffix aliasing, `null` for bass.

**Acceptance:** this suite passes unchanged after phases C and D. Any intentional contract change must be called out explicitly and justified, not absorbed silently into a test edit.

### Phase B — Package gap-closing, published as 0.3.0

1. **`(key, suffix)` lookup** returning the existing `GuitarChordResult` shape, keyed on chords-db's own raw key spellings (`Csharp`, `Eb`, `Fsharp`) so `apiFrame` keeps its current request semantics and error text. Distinct from `lookupGuitarChord`, which takes a parsed label.

2. **Library enumeration** — an **iterator over entries and positions**, not merely a key list. `ChordWorkbench.buildPresets` needs to walk the library, and an iterator lets a future similarity or filtering feature build its own index without another package release. Keys and suffixes exposed alongside.

3. **Power chords extended to bass.** `powerChordPosition` currently hardcodes `INSTRUMENTS.guitar`. Generalise to `bass4` and `bass5`. Diff the generated shapes against frames' hand-fingered `BASS_PRESETS` and keep frames' if they differ musically — report the comparison rather than assuming equivalence.

4. **Publish `@pepperhorn/chordl-guitar@0.3.0`** to npm.

**Gated on:** `feat/guitar-foundations` being merged, which it now is (PR #17). **Update 2026-09-07:** 0.2.0 is no longer just "on `main`" — it was published to npm on 2026-09-01, so 0.3.0 is now a second release rather than the package's first, and the registry path this whole design depends on is proven rather than assumed.

### Phase C — Chord and scale migration (scoped, not yet designed)

- ~~Add the registry dependency~~ — **already done, out of order.** See below. Bump the range to `^0.3.0` once phase B publishes; retire `src/lib/instruments.ts` and `src/lib/notes.ts`
- Alias `"bass"` → `bass4` at the API boundary so the public value keeps working
- Preserve `positionIndex` semantics by indexing the raw `positions` array
- Keep `patch` and `presetSource` local
- `Object.keys(INSTRUMENTS)` currently drives the instrument tab list in both workbenches; the package's five ids would render bass5 in chord and scale mode, which has never been supported. The UI list must become explicit rather than derived.

### Phase D — Tab migration (scoped, not yet designed)

Separate from C deliberately: the tab module carries its own instrument universe and the high→low `openMidi` trap. Folding it into C would put the riskiest silent-failure mode in the same change as everything else.

- Retire `tab/instruments.ts`, `tab/pitch.ts`, `tab/chordLookup.ts`
- Reverse `openMidi` at the point of use, or convert `pitch.ts` to index low→high
- Keep the soundfont `patch` map local
- Collapse `InstrumentUi` into the package's ids

### Phase E — `scales.ts` split (scoped, not yet designed)

`src/lib/scales.ts` (251 lines) divides three ways: general theory (`SCALES`, `noteToPitchClass`, `pitchClassToName`, `intervalToDegree`) → `chordl-core`; fretboard-specific (`POSITIONS`, `noteAt`, `resolveWindow`, `generateScale`) → `chordl-guitar`; frames presentation (`SCALE_LABELS`, `makeBlankScaleFrame`, `mergeDots`, dot styling) stays.

Four exports have a runtime dependency on `INSTRUMENTS`, reading only `.strings`, `.tuning`, and `.frets` — all present in the package's config, so that dependency swaps cleanly once ids are reconciled. `openStringPitchClass` derives pitch class from the tuning *letter*, losing octave; the package's `openMidi` would serve it strictly better.

## What has already happened in frames (2026-09-07)

One piece of real migration work landed outside this phase sequence, and anyone resuming should know about it before re-reading phase C.

`frames` commit `6d7377b` (PR #5, 2026-09-02) added `"@pepperhorn/chordl-guitar": "^0.2.0"` to `package.json` and replaced frames' hand-maintained top-3 table with a re-export: `src/lib/staticPresets.ts` now does `export { GUITAR_TOP3_PRESETS } from "@pepperhorn/chordl-guitar";`. The local copy had drifted ten chords behind the package, so the change was worth making on its own merits.

Two consequences worth being explicit about:

- **The registry path is proven.** This design's central bet — that frames consumes the package from npm rather than through `file:` or a workspace, leaving the Dockerfile untouched — is no longer a prediction. It installs, builds and ships.
- **It landed without phase A.** No characterization tests existed when it went in, so the top-3 swap was made without the safety net this design says must come first. It is a narrow, verifiable change and nothing suggests it broke anything, but it is precisely the pattern phase A exists to prevent, and the next such change will not be as narrow.

Everything else in phases C, D and E is untouched: `src/lib/instruments.ts` and `src/lib/notes.ts` still exist and are imported in ten places, `"bass"` is still a native id rather than an alias to `bass4`, both workbenches still derive their instrument tab list from `Object.keys(INSTRUMENTS)`, `tab/instruments.ts` still stores `openMidi` high→low, and `scales.ts` is still one 251-line file.

## Testing strategy

Phase A's suite is the acceptance criterion for C and D. Neither lands without it green.

Phase B follows the package's existing practice: derived values verified against real chords-db data rather than against hand-written expectations, as the 4,183-position golden test does for `positionToMidi`.

## Risks

| Risk | Mitigation |
|---|---|
| String-order flip produces wrong pitches silently | Phase A pins `pitch.ts` behaviour before D touches it; ukulele's reentrant tuning is the canary |
| `positionIndex` shifts under callers | Index the raw `positions` array only, never a selected subset; phase A pins boundary cases |
| Publishing cadence slows iteration | Accepted — it is the cost of the only deployable option |
| Agents editing outside their worktree | Observed once during sub-project 1b: a subagent wrote a changelog entry into the parent repo as well as its worktree. Check parent-repo status after each dispatch, not only at the end |
